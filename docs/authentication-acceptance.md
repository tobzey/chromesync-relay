# Live 1Password acceptance

Code and synthetic browser tests do not prove that a particular live 1Password enrollment or website works. This runbook is the remaining deployment acceptance step. Use a disposable test account and an explicitly restricted vault before enrolling valuable accounts. Never paste a service-account token, password, OTP seed/code, Secret Key or recovery code into an agent conversation.

## Required setup

1. Select an always-on Mac or Linux executor outside the agent's OS authority. Install the reviewed ChromeSync source, Node 22+, its OS credential-store backend and a current compatible Chrome for Testing or Chromium. Install the pinned SDK with `npm ci --prefix auth --ignore-scripts`.
2. Select the existing relay deployment and admit independent authentication rooms for the executor's agent and approver pairings. Apply the interactive rate budgets in [authentication setup](authentication.md). The relay receives no provider credential.
3. Create a custom 1Password test vault with the chosen disposable accounts. Provision read-only service-account access to that vault. Enter the token yourself in the trusted approval inbox's connection form and leave account discovery enabled. This is a one-time connection, not a per-account JSON enrollment. The value is stored on the executor; the agent receives no provider credential or reference-resolution operation. Account titles and saved website origins are intentionally visible to authorized discovery clients.
4. For passkeys, run `chromesync auth passkey-setup` on the trusted executor. Install the official 1Password extension in the dedicated profile and sign in yourself with an identity restricted to the test vault. Do not use the owner's unrestricted vault identity with only a visibility filter.
5. Start with `chromesync auth open --url URL`, then search, select an account, observe and request authentication using the current revision. The selected account and exact origin are bound by the runtime; no hand-written flow is required for adaptive sign-in. If a service needs tested selectors or separate sensitive-reauthentication permissions, use the inbox's optional advanced configuration. Such flows require exact origins, private item/field references and an expected account marker. For passkeys, start at the actual WebAuthn origin. Configured flows can set an explicit same-origin `passkey.receiverUrl` when the origin root redirects elsewhere.

The user performs real credential provisioning and provider sign-in through the trusted UI. Agent-readable terminal output can contain pairing metadata, selected account titles/origins, opaque handles, request IDs and fixed outcomes. Successful handoff also prints the local destination profile and debugging endpoint. It must not print provider values or the cookie bundle. The agent deliberately receives the destination session's authority; it must not have filesystem or debugger access to the executor. An existing cookie-sync relay can be reused after its authentication room admission and interactive rate budgets are verified.

## Acceptance sequence

| Check | Procedure | Required evidence |
| --- | --- | --- |
| Catalog scale | Search the connected vault by exact website and by name, following returned cursors. Record its existing item count; do not create thousands of live accounts for this check. The automated fixture already covers 3,000 synthetic entries. | Expected matches are reachable in bounded pages of at most 20. Results contain only item handles, titles, website origins and match kind; no credential values, usernames, field contents, vault references or provider errors. Record live SDK latency separately from synthetic scale results. |
| Duplicate accounts | Use two distinct items with identical titles and the same website, select each in a fresh discovery session, and inspect the owner request. | Distinct handles remain distinct account resources and policies. No automatic account merging or reuse of one account's permission for the other. The owner can verify which account actually signed in before handoff. |
| Name-only match | Search for an entry whose saved website differs from the actual login origin. | The owner sees both origins and a name-match warning. Search and selection alone do not fill credentials or grant a saved permission. |
| Discovery disabled | Disable account discovery for the connection in the inbox, then search and try an earlier handle. | The disabled connection supplies no new discovery results and its earlier selection cannot authorize a new account binding. Existing explicit account permissions remain a separate policy decision. |
| Once | Agent opens the login URL, selects its catalog account and requests password/TOTP. Owner allows once. | Original browser reaches the correct account; the next fresh session requires approval. Unconfigured or ambiguous forms go to protected owner interaction without resubmitting a completed action. |
| Deny | Deny a fresh request. | No provider credential is supplied; agent receives denied. |
| Factor scope | Save password-only permission for a request that includes TOTP. | TOTP is withheld; request requires additional approval or owner recovery. |
| Offline daily driver and stable account | Save a password/TOTP rule for a site with working automatic account verification, then stop the approver process or power off that device. Open another session, search again and select the same unchanged item, origin and method using a fresh handle. | The stable account ID and enrollment version preserve the saved policy. Executor retrieves the current credential and fresh OTP; correct-account login succeeds without an approver connection. A different item, origin, method or changed enrollment does not inherit that permission. If the site needs owner confirmation, record that offline completion is unsupported for that site. |
| Sensitive reauthentication | Use a configured flow with a separate `reauthentication` purpose. Give routine login permission only, then trigger a sensitive action in the same protected browser session. | A new request explicitly identifies reauthentication; login-only permission does not authorize it. Adaptive mode currently classifies prepared challenges as login and cannot establish this purpose separation by itself. |
| Passkey | Request the test service's passkey, approve, and use the protected receiver view for provider selection/unlock when required. | Original challenge succeeds at the service for the expected account; no private key or raw credential result appears in the agent channel. |
| Wrong account | Select another account in the provider, or make the test service show a different account identity. | Configured success and adaptive automatic identity verification reject the mismatch. When adaptive mode requires owner verification, the owner leaves the confirmation box unchecked; neither a successful signature nor a generic success page is treated as the selected account. |
| Owner confirmation | Finish a catalog request in the protected view when no automatic identity signal is available. Try completion before checking the account-confirmation box, then verify the actual account and check it. | No completion call is sent while unchecked. The controller also refuses completion while a credential challenge remains. Confirmation is reset for each takeover and invalidated by document navigation or a new challenge. |
| Local handoff | After a request succeeds, run `chromesync auth handoff --session SESSION`. Connect to its returned local browser endpoint and open an account-specific page on the real destination site. | Import returns `imported` only after cookie readback. Independently verify the expected account is actually logged in in the destination browser before the agent continues. CLI output, non-browser files and relay logs contain no cookie bundle or 1Password values. A cookie readback alone does not pass the destination-login check. |
| Handoff account isolation and interruption | Reuse a destination profile name for a different account/origin; interrupt an import; request another export after a newer request is pending or denied. | A mismatched profile is refused, partial imports report `needs-retry`, and an older successful request cannot authorize the later export. A retry for the same account can complete without mixing prior imported cookie identities. |
| Locked receiver | Lock 1Password or restart the receiver before a passkey request. | Either ordinary provider verification completes or a bounded needs-user outcome appears; no verification is fabricated. Record whether this enrollment can operate without a present user. |
| Recovery | Interrupt a ceremony, reload the inbox, and use protected takeover or Review and retry. | A fresh decision is required for retry; an accepted website submission is not blindly repeated. |
| Revocation | Revoke a saved policy or the requesting device and attempt another request. | Policy requires approval again, or revoked device cannot open/control a browser. |
| Restart | Stop the executor during authentication, restart it, and inspect the request. | Interrupted work is unresolved; a previous sensitive action is not automatically repeated. |

Record the tested service, date, browser/extension versions, executor OS, catalog size, request outcomes, account-verification method, destination-login result and whether provider unlock required interaction. Keep the record free of values and screenshots of real credential fields. Handoff moves only an exact-host cookie snapshot; it does not move local storage, session storage, IndexedDB, parent-domain cookies, device binding or arbitrary pending transaction state, and it does not continuously propagate later logout. Use these observations to declare compatibility for that service and enrollment; they do not establish universal support for every website or factor.

## Passkey and phone limits

Password/TOTP unattended access uses the supported 1Password SDK. Existing passkeys currently use the independently enrolled normal 1Password extension because the public SDK does not expose passkey signing. Catalog passkey setup creates exact-origin bridge permissions for the selected discovery session; it does not turn the selected catalog item into a provider credential-selection guarantee. “Always allow” removes ChromeSync's next approval prompt; it does not remove 1Password's own unlock, selection, touch or biometric requirements. Headless and unattended real-provider passkeys remain acceptance questions, not established support. Native operating-system prompts may require access to the executor itself.

APNs/FCM and a native phone app are future clients of the same approval protocol. The desktop inbox is implemented; a mobile push app is not part of this release.
